# 量化指增周报：版本进度与 V2/V3 数据路线图

> 更新日期：2026-09-19  
> 当前版本：V2A  
> 当前状态：V1 和 V2A 可按周离线生成；V2B/V3 尚未实施

## 1. 当前结论

| 版本 | 目标 | 当前状态 | 是否可用 |
|---|---|---|---|
| V1 | 用既有 SQLite 和基准净值生成可复核周报 | 核心功能完成 | 是 |
| V2A | 用风格指数代理解释市场风格背景 | 12 条日线、10 个代理、滚动窗口、类别结论和12周热力图已实现 | 是 |
| V2B | 解释宽度、截面分化、成交与个股波动环境 | 缺全A股票日行情与 point-in-time 历史成分权重 | 否 |
| V3 | 真实产品研究、风格漂移、智能叙事和分发归档 | 已形成路线图，尚未建立产品主数据和研究数据层 | 否 |

当前真实产物以 2026-09-11 为截止日，覆盖 300、A500、500、1000、2000 五类指增，共 217 条有效“管理人 × 策略”当周观测，周超额字段覆盖率为 100%。当前有 4 条 Watchlist 数据缺失提示，均已在报告中明确展示。

## 2. V1 已实现范围

### 2.1 数据链路

```text
cc_data.sqlite3 + benchmark_nav.json + style_index_nav.json + YAML 配置
                      ↓
               只读 analytics 层
                      ↓
       report_facts.json（可复核事实）
                      ↓
          Markdown 周报（确定性模板）
```

- SQLite 使用只读模式，并预检必需表与字段。
- 指定历史 `--as-of` 时，所有下游分析均先裁剪至截止日，避免未来数据泄漏。
- 基准日期缺失时只向前寻找最近可用交易日，不使用未来 NAV。
- 事实计算和文字渲染分离；Markdown 不重新计算指标。
- 同一报告日期默认不覆盖，只有显式传入 `--overwrite` 才允许重生成。
- V2A 风格日线在报告生成前独立更新并缓存；生成周报时绝不联网。

### 2.2 已实现功能

| 模块 | 已实现内容 |
|---|---|
| 市场与基准 | 本周、近 4 周、近 12 周基准收益；首周锚定上一年 12 月 31 日；V1 大小盘代理 |
| V2A 风格层 | 12 条风格指数日线、10 个收益差代理、本周/4周/12周、类别结论、连续同向、12周切换次数与热力图 |
| 指增横截面 | 管理人×策略周收益、超额中位数、P25/P75、分化度、正超额比例、样本数 |
| 管理人排名 | 周超额排名、同类百分位、排名变化、本周靠前/靠后名单 |
| 近期趋势 | 近 4/12 周超额简单加总、正超额比例、连续正负超额 |
| 超额回撤 | 复用数据库正式 `ytd_excess_drawdown`；识别历史尾部及首次明确修复 |
| Watchlist | 衍复、孝庸、平方和、顽岩、华年；支持标准名称、别名、缺失观测提示 |
| 异常检测 | 周度前后 10%、2σ、连续正负、4 周前后 10%、百分位跳变、回撤尾部及修复 |
| 数据质量 | 缺失策略、样本不足、字段覆盖率、基准实际取值日、Watchlist 缺失 warning |
| 工程能力 | CLI、原子写入、按日期留档、Makefile 接入、无网络验证、自动化测试 |

### 2.3 当前指标口径

- 报告实体是“管理人 × 策略”，不是数据库中真实的基金产品。
- 五类指增的周超额直接读取 `weekly_performances.weekly_excess`，analytics 层不重算第二套超额。
- 因此 V1 不能笼统称为“统一几何超额”。量化选股在导入阶段使用几何超额，但不属于当前五类指增周报范围。
- 近 4/12 周管理人超额为正式周超额的简单加总，并在 facts 中记录为 `simple_sum_of_weekly_excess`。
- 基准近 4/12 周收益使用 NAV 起止比计算，是几何累计收益：

```text
基准 N 周收益 = NAV(报告截止日) / NAV(N 周前报告日) - 1
```

- 报告模板固定按 `300 → A500 → 500 → 1000 → 2000` 展示策略与基准；管理人变化、同一管理人 Watchlist、异常列表均遵守该顺序。

### 2.4 当前命令与产物

```bash

make weekly-report-validate

# 仅生成最新周报
make weekly-report

# 更新基准、导入数据、重建 Dashboard、生成周报
make update-all

# 同一报告日期确认覆盖
cd backend && python3 scripts/generate_weekly_report.py --overwrite --print-summary
```

产物：

- `reports/weekly/{as_of_date}.md`
- `data/derived/weekly/{as_of_date}/report_facts.json`
- `data/derived/weekly/{as_of_date}/report_validation.json`

## 4. V2 规划：市场 Alpha 环境解释

### 4.1 V2A 已实现：风格指数代理

V2A 已接入 12 条风格价格指数的本地日线缓存，并在周报中输出 10 个代理的本周、近 4 周、近 12 周收益差、连续同向周数、12 周切换次数、方向热力图和类别风格结论。只有同一维度的全部配置代理均有数据且同向时才输出占优/不占优；本周与近 4 周反向只标为“短线反转，尚待确认”，不把它写成已确认的趋势切换。默认中性阈值为 0.05%，实际取值日最多允许滞后 4 个自然日，且正长度窗口必须包含新增指数观测。

- 更新命令：`make update-style`；数据写入本地 `style_index_nav.json`，不提交 Git。
- 周报生成命令：`make weekly-report`；只读缓存，不联网。
- 收益口径：各腿以窗口起止 NAV 计算累计收益，再取“多头腿收益 − 对照腿收益”；不累加单周差值，不将其表述为产品几何超额。
- 代理及代码见 [V2 风格数据标的清单](V2_STYLE_DATA_INSTRUMENT_LIST.md)。

### 4.2 V2B 目标

V2 要回答的不只是“本周指增表现如何”，还要回答：

> 本周是否具备较好的选股宽度和截面分化？成交、波动和风格是否有利于量化选股？不同指数池的 Alpha 环境是否出现明显差异？

### 4.3 拟新增能力

| 模块 | 拟新增指标 | 主要用途 |
|---|---|---|
| 市场宽度 | 全 A 上涨比例、下跌比例、涨跌停比例、指数成分股胜率 | 判断机会是否广泛分布 |
| 截面分化 | 全 A/各指数池个股收益标准差、收益分位差 | 判断选股空间大小 |
| 交易环境 | 成交额、换手率、成交额变化、流动性分层 | 判断策略容量与交易难度 |
| 波动环境 | 指数实现波动率、个股波动率中位数、波动分层 | 判断风险与可交易机会 |
| 风格代理 | 大小盘、成长/价值、动量、低波、红利 | **V2A 已实现**；识别指增收益的风格背景 |
| 稳定性 | 风格方向连续性、风格切换频率、12 周热力图 | 判断环境是否稳定或快速轮动 |
| 环境标签 | 选股宽度、截面分化、流动性、风格稳定度 | 形成可复核的 Alpha 环境结论 |

### 4.4 V2B 必需数据

#### A. 股票日行情面板

最低字段：

```text
trade_date
security_id / windcode
close / adjusted_close
daily_return
amount
volume
turnover_rate
is_trading
is_st
listing_date
```

用途：全 A 宽度、截面收益标准差、成交环境、换手率、实现波动率、动量和反转代理。

要求：

- 必须使用统一复权口径，禁止跨周混用前复权、后复权和不复权数据。
- 停牌、上市不足一定天数、ST 和退市整理期股票需有明确处理规则。
- 每个报告日都要记录实际行情截止日和有效股票数量。

#### B. 指数成分与权重的历史快照

最低字段：

```text
index_code
effective_date
security_id
weight
```

覆盖指数：沪深300、中证500、中证1000、中证2000、A500。

用途：计算各指数成分股胜率、指数池截面分化、指数池成交和波动环境。

要求：必须是 point-in-time 历史成分，不能用当前成分回填历史，否则会产生幸存者偏差和未来信息泄漏。

#### C. 风格数据

V2 可分两档实施：

1. **最小可行版（V2A，已完成）**：接入大小盘、成长/价值、红利、动量、低波等风格指数日行情，用指数收益差构造风格代理。
2. **增强版**：接入股票级市值、估值、盈利、成长、波动、动量等因子暴露，构建统一的截面因子组合。

已整理 Wind 标的、查询键、代理配对与取数验收规则，详见 [V2 风格数据标的清单](V2_STYLE_DATA_INSTRUMENT_LIST.md)。

增强版最低字段示例：

```text
trade_date
security_id
market_cap
book_to_price / earnings_yield
profitability
growth
momentum
volatility
industry_code
```

#### D. 交易日历和基础证券主表

需要统一的 A 股交易日历、证券代码映射、上市/退市日期、交易状态和行业分类。它们用于日期对齐、缺失判断和跨数据源代码统一。

### 4.5 V2B 数据源决策

正式开发前必须先确认：

- 主数据源及许可范围，例如 Wind、内部行情库或官方交易所/指数公司数据。
- 是否能取得历史指数成分及权重快照。
- 日行情的复权、停牌、涨跌停和上市天数规则。
- 风格层先采用“风格指数代理”还是直接建设股票级因子层。
- 数据是否允许写入仓库；若不允许，应只保存在本地数据库或受控数据目录。

V2 不应从临时网页或报告文字中拼接核心数值。所有市场环境结论必须进入结构化 facts，并记录来源、截止日、样本量和缺失规则。

### 4.6 V2B 建议实施顺序与验收

1. 建立市场数据字典和 point-in-time 规则。
2. 先实现全 A 宽度、指数池胜率、截面分化、成交额和波动率。
3. 再实现风格指数代理和环境标签。
4. 将 V2 facts 接入固定 Markdown 模板和 12 周热力图。
5. 用至少 12 周历史数据回放，检查标签稳定性和未来数据泄漏。

验收标准：相同输入必须得到相同环境标签；每一个标签都能定位到具体指标、日期、样本数和阈值。

## 5. V3 规划：真实产品研究与智能叙事

### 5.1 目标

V3 将“管理人 × 策略”的行业横截面报告升级为真实产品研究系统，并增加研究资料关联、风格漂移监控、受约束的智能叙事以及自动分发归档。

### 5.2 建议拆分

| 阶段 | 能力 | 前置条件 |
|---|---|---|
| V3A | 真实产品主数据与净值层 | 产品唯一标识、标准名称、策略、基准、净值历史 |
| V3B | 产品风险、相关性、滚动 beta、风格漂移 | 足够长的产品净值、基准与风格序列 |
| V3C | 研究资料关联和 LLM 叙事 | 结构化 facts、研究资料索引、引用和权限规则 |
| V3D | HTML/PDF、邮件、知识库归档、版本比较 | 稳定模板、收件人与归档权限、历史版本库 |

### 5.3 V3 必需数据

#### A. 产品主数据

```text
product_id（稳定唯一标识）
product_name
manager_id / manager_name
strategy_key
benchmark_key
inception_date
termination_date
share_class
nav_frequency
currency
aum（如可得）
```

必须解决产品更名、同名产品、管理人名称变更、不同份额和策略迁移问题。不能继续用“管理人 × 策略”作为产品替代品。

#### B. 产品净值和收益

```text
product_id
nav_date
unit_nav / accumulated_nav
return
nav_status
source
source_timestamp
revision_id
```

要求保留原始值、修订记录和数据来源，支持周频不齐、补录、撤销和净值更正。

#### C. 产品持仓、交易和风险暴露（若可取得）

```text
product_id
as_of_date
security_id
weight
industry
factor_exposure
gross_exposure / net_exposure
cash_ratio
turnover
derivative_exposure
```

用途：行业和因子归因、真实风格漂移、容量和拥挤风险分析。若拿不到持仓，V3B 只能基于净值相关性和 beta 做弱识别，不能声称完成真实归因。

#### D. 研究资料与管理人事件

需要可检索并带元数据的尽调报告、访谈纪要、周报、公告、团队/AUM/策略变化等资料：

```text
document_id
manager_id / product_id
document_date
document_type
title
source
tags
access_level
content_reference
```

LLM 只能引用有日期、有来源、有权限的材料；研究叙事必须区分事实、推断和待确认事项。

#### E. 报告版本和分发数据

```text
report_id
as_of_date
analytics_version
input_fingerprint
facts_hash
template_version
generated_at
recipient / archive_target
delivery_status
```

用途：报告版本比较、历史异常追踪、邮件/知识库归档和审计。

### 5.4 V3 智能叙事边界

- Python 继续负责所有数字、排名、阈值、回撤、beta 和异常判断。
- LLM 只接收通过 schema 校验的 facts 和获准引用的研究资料。
- LLM 不直接查询生产数据库，不补造缺失数字，不把相关性写成因果。
- 每段研究结论应能回溯到 facts 字段或具体资料来源。

### 5.5 V3 验收标准

- 同一管理人与真实产品可以分别分析，且不会因重名、别名或份额产生重复。
- 净值修订后可以重建指定历史报告，并保留旧版本差异。
- 风格漂移和 beta 有明确窗口、基准、最小样本和显著性规则。
- LLM 输出不新增 facts 中不存在的数字，引用能够定位原始资料。
- HTML/PDF、邮件或知识库归档有明确权限、收件人和投递状态。

## 6. 升级建议

当前最合理的下一步不是直接接入 LLM，而是先做 V2 数据可用性审计：确认股票日行情、历史指数成分和风格数据是否可持续取得。V2 数据字典和 point-in-time 规则稳定后，再建设市场环境 facts。

进入 V3 前，必须先完成产品主数据设计并取得真实产品净值。没有稳定 `product_id` 和可追溯净值时，不应开展产品级归因、风格漂移或自动研究叙事。
